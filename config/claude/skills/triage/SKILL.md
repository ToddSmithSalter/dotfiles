# Triage

Move issues on GitLab through a small state machine of triage roles.

Merge requests are triaged too when the maintainer names one: **an MR is an issue with attached code**, using the same roles, same states, and same machine, with a few deltas marked "for an MR" below. Discovery lists issues only unless the maintainer asks for MRs.

Every note or issue posted to GitLab during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md): how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): how the `.out-of-scope/` knowledge base works

## GitLab

All work lives on GitLab. Use the `glab` CLI. It infers the project from `git remote -v` inside a clone. For anything beyond the commands below, call the Skill tool with "gitlab-cli-skills".

- **Read an issue**: `glab issue view <n> --comments`
- **List issues**: `glab issue list -F json`, with `--label` filters
- **Create an issue**: `glab issue create --title "..." --description "..."`, using a heredoc for a multi-line description
- **Comment**: `glab issue note <n> --message "..."`. GitLab calls comments "notes".
- **Label**: `glab issue update <n> --label "..."` and `--unlabel "..."`. Comma-separate several labels, or repeat the flag.
- **Close**: `glab issue close <n>`. It accepts no closing comment, so post the note first, then close.
- **MR equivalents**: `glab mr view <n> --comments`, `glab mr diff <n>`, `glab mr list -F json`, `glab mr note`, `glab mr update --label`/`--unlabel`, `glab mr close`.

GitLab numbers the two surfaces separately: `#42` is issue 42, `!42` is merge request 42. Use that syntax so no reference is ambiguous. Ask which surface the maintainer means when they give a bare number.

## Project docs

Before exploring the codebase, read `CONTEXT.md` at the repo root, or `CONTEXT-MAP.md` and the per-context `CONTEXT.md` files it points to. Read the ADRs in `docs/adr/` that touch the area. If these files do not exist, proceed silently.

## Labels

Teleo's GitLab labels are the whole vocabulary. Apply them exactly as written, capitals and spaces included. Never create a new label. Never apply `To Do`.

**Type. Exactly one, on every triaged issue:**

- `Bug`: an unexpected problem or unintended behavior
- `Feature`: a new feature request, specified well enough to build
- `Idea`: a feature or enhancement that still needs discussion
- `Refactor`: a code refactor for performance or developer experience

**Priority. On a `Bug` only, exactly one. Never put a priority label on anything else:**

- `High Priority`: fix within the next 24 hours
- `Medium Priority`: fix within the next week
- `Low Priority`: not urgent, no impact on the user experience

**Area. Add alongside the type label when it applies:**

- `CI/CD`: testing or deployment pipelines
- `Devices`: Talon or Insight devices

**Open questions:**

- `To Investigate`: the issue needs information or investigation before anyone acts on it

**Closing:**

- `Won't Fix`: work will not continue
- `Invalid`: no longer relevant
- `Duplicate`: another issue or merge request already covers it

`Doing` means someone is working on the issue right now. The person doing the work applies it. Triage does not.

## States

There is no "ready" label. An issue is ready when it carries a type label, carries no `To Investigate`, and has an Agent Brief note.

- **Untriaged**: no type label.
- **Waiting on the reporter**: `To Investigate`, plus a Triage Notes note holding the open questions.
- **Ready for an agent**: a type label, no `To Investigate`, and an Agent Brief note.
- **Ready, but human only**: the same, and the brief says why a human must do it. Assign the person when you know who.
- **Closed**: `Won't Fix`, `Invalid`, or `Duplicate`.

For an MR, the same states read against the attached code. A brief on an MR says what is left to do to the diff. Human only means a person must merge it.

Every triaged issue carries exactly one type label. A `Bug` carries exactly one priority label as well. If the labels conflict, flag it and ask the maintainer before doing anything else.

Transitions: an untriaged issue gets its type label first. `Idea` becomes `Feature` once grilling has specified it. `To Investigate` comes off when the reporter answers. The maintainer can override at any time; flag transitions that look unusual and ask before proceeding.

## Invocation

The maintainer invokes `/triage` and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue) or "let's look at !42" (merge request)
- "Label #42 as a High Priority bug"
- "What's ready for agents to pick up?"

## Show what needs attention

Query GitLab and present three buckets, oldest first:

1. **No type label**: never triaged.
2. **`To Investigate` with no reporter reply since the last Triage Notes note**: still waiting.
3. **`To Investigate` with a reporter reply since the last Triage Notes note**: needs re-evaluation.

When the maintainer asks for MRs as well, include external MRs in these buckets and tag each line `[MR]` or `[issue]`. Discovery surfaces only *external* MRs, meaning MRs whose author is not a project member, so a colleague's in-flight MR is not triage work. This filter is discovery-only; a named MR is always triaged regardless of author.

Show counts and a one-line summary per item. Let the maintainer pick.

When the maintainer asks what is ready for agents to pick up, list open issues that carry a type label, carry neither `To Investigate` nor `Doing`, have no assignee, and have an Agent Brief note.

## Triage a specific issue or MR

1. **Gather context.** Read the full issue or MR (body, notes, labels, author, dates; for an MR, the diff too). Parse any prior triage notes so you don't re-ask resolved questions. Explore the codebase using the project's domain glossary, respecting ADRs in the area. Run two checks against the codebase: (a) **redundancy**: search for an existing implementation of the requested behavior by domain concept (not just the request's wording), and report where you looked. If found, it is already implemented, so close it (step 5). (b) **prior rejection**: read `.out-of-scope/*.md` and surface any that resembles this request.

2. **Recommend.** Tell the maintainer your type and state recommendation with reasoning, plus a brief codebase summary relevant to the request (including whether it's already implemented). Wait for direction.

3. **Verify the claim.** Before any grilling, check that the claim holds up. For a bug, reproduce it from the reporter's steps. For an MR, confirm the diff does what it claims: check it out with `glab mr checkout <n>`, run the relevant tests or commands. Report what happened: confirmed (with code path), failed, or insufficient detail (a strong `To Investigate` signal). A confirmed verification makes a much stronger agent brief.

4. **Grill (if needed).** If the request needs fleshing out, call the Skill tool twice, for "grilling" and "domain-modeling", and grill it into shape a round of questions at a time, sharpening domain terms and updating `CONTEXT.md`/ADRs inline as decisions land.

5. **Apply the outcome:**
   - **Ready for an agent**: apply the type label, and the priority label for a `Bug`. Remove `To Investigate`. Post an agent brief note ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - **Ready, but human only**: the same, with a brief that says why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - **Waiting on the reporter**: apply `To Investigate` and post triage notes (template below).
   - **Closing.** Post the note first, then close, because `glab issue close` accepts no closing comment. Apply the label that says why:
     - **Already implemented**: apply `Invalid`, because the request is no longer relevant. Point to where the behaviour already lives; do **not** write to `.out-of-scope/` (that KB is for *rejected* requests, not built ones).
     - **Already covered elsewhere**: apply `Duplicate` and link the issue or MR that covers it.
     - **Rejected (bug)**: apply `Won't Fix`, give a polite explanation, then close.
     - **Rejected (enhancement)**: apply `Won't Fix`, write to `.out-of-scope/`, link to it from a note, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - **Still untriaged**: apply the type label you are confident about, and `To Investigate` if it needs more work.

## Quick state override

If the maintainer says "label #42 as a High Priority bug", trust them and apply the labels directly. Confirm what you're about to do (label changes, note, close), then act. Skip grilling. If they mark an issue ready without a grilling session, ask whether they want an agent brief.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist on the issue or MR, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.
